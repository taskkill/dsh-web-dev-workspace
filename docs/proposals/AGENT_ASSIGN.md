# 工作台「指定 Agent 干活」设计方案（Proposal）

> 状态：**已按 MVP 实现（v1.2.75）**｜日期：2026-10-27｜作者：Lead + UI 设计师｜适用范围：Dev Workspace 工作台
> 实现见 [docs/pipeline/design.md](../pipeline/design.md)、[assignments.js](../../dsh-web-filebrowser-plugin/assignments.js)、[client.js](../../dsh-web-filebrowser-plugin/client.js)（工作台「团队与指派」卡）；验收步骤见 [ACCEPTANCE 批次 12](../ACCEPTANCE.md)。
> 关联：[PLAYBOOK](../PLAYBOOK.md) · [AGENT_TEAM](../AGENT_TEAM.md) · [团队角色手册](../opc/README.md) · 效果图：[mockups/](mockups/)

## 0. 一句话结论

**可以，而且不需要新造一套 Agent 运行时。** 推荐 MVP：在工作台加一张「**团队与指派**」卡片——选角色/成员 → 写任务（可关联流水线阶段或作为临时任务）→ 生成**结构化指派单**投递到当前对话，由 Lead 用 Harness 原生 Agent Teams 工具（`spawn_teammate` / `send_message` / `team_task_*`）执行；成员与共享任务状态复用原生「团队」面板，插件只负责**项目侧的指派、留痕与状态桥**，不重复实现团队通信。

## 1. 现状与问题

| 现在能做什么 | 缺口 |
|---|---|
| 工作台按阶段「启动并派发」：把角色提示词发到当前对话 | 只能派「阶段角色」，不能指定具体成员（如 `opc-dev`）做一件具体小事 |
| Harness 原生「团队」面板：成员 roster（角色/状态/模型/当前任务）、共享任务（状态/依赖/写范围） | 与「当前项目」脱节：不知道这次指派属于哪一轮、哪个阶段、验收标准是什么 |
| 对话里让 Lead 临时 `spawn_teammate` / `send_message` | 口述派单容易漏：任务边界、验收、产物路径、关联阶段不清楚，事后难追溯 |
| 流水线有七阶段 + 双复核 | 「临时任务」（不改变流水线）没有入口，Owner 只能口头让 Lead 做 |

核心问题：**Owner 缺少一个「项目内的派工台」**——把「谁、做什么、做到什么程度、属于哪一关、产出放哪」一次性说清，并且留痕可查。

## 2. 目标与非目标

**目标**
1. 在工作台内完成「选 Agent → 写任务 → 指派 → 追踪」闭环，不离开工作台/对话。
2. 指派单结构化（角色、任务、验收、关联阶段、期望产物、优先级），Lead 可直接执行，不再靠口述。
3. 与现有七阶段双复核兼容：关联阶段的任务走流水线闸门；临时任务不改变流水线，但必须有验收与产物。
4. 留痕：每次指派写入本工作区 `.dsh/agent-assignments.json`，可在卡片上查看历史。
5. 不重复实现团队面板：成员实时状态、共享任务依赖仍以 Harness 原生「团队」面板为准（提供跳转/联动）。

**非目标**
- 不在插件内重建 Agent 运行时、消息队列或团队 UI。
- 不允许绕过 approval/release 人工闸门；不允许 Agent 自派任务。
- 不做跨工作区/远程 SSH 的团队状态（SSH 工作区暂不支持流水线类功能）。

## 3. 三种实现路线（已做技术核查）

| 路线 | 做法 | 可行性 | 结论 |
|---|---|---|---|
| **A. 前端编排（MVP）** | Workbench 卡片生成结构化指派消息 → 发到当前对话（复用现有 `sendPromptText` 机制）→ Lead 用原生团队工具执行；指派记录由插件本地保存与展示 | 高：零新 Host 服务、零权限风险、与现有「启动并派发」同机制 | **推荐先做** |
| **B. 团队状态只读桥** | Host 注入 `agentTeams` 服务读取 roster/任务，在卡片显示成员实时状态 | 中：原生 `TeamService` 的读写方法（`listMembers`/`spawnTeammate`/`createTask` 等）要求**活的 Agent 调用者凭证**；Owner 面板没有 Agent 身份。只读展示也需 Harness 暴露 owner 级 API | 等上游能力，MVP 用「打开团队面板」链接替代 |
| **C. 原生直接派工** | Workbench 直接调用团队服务/新建成员并唤醒 | 低（当前）：无 owner 级团队 API；直接调用会破坏「只有 Lead 能组队」的权限模型 | 不建议（会与 Harness 团队面板重复/冲突） |

> 结论：**A 立刻可用；B/C 等 Harness 提供 owner 侧 Agent Teams API 后再升级**。这也符合插件边界「不重复实现团队通信」。

## 4. 推荐 MVP：工作台「团队与指派」卡

### 4.1 位置与信息架构

工作台卡片顺序（现有）：`需要你处理 → 交付前体检 → 本轮变更 → 需求与调整 → 项目状态 → 项目流程 → 设计稿 → 验收 → 运行中`。

新增卡片 **「团队与指派」**，放在「项目状态」与「项目流程」之间（效果图示例顺序：`需要你处理 → 项目状态 → 团队与指派 → 项目流程`）——「需要你处理」保持最高注意力；团队/指派属于项目级上下文，不打断闸门操作，也不淹没项目进度。

```
┌─ 团队与指派 ────────────────────────────── [打开团队面板 ↗] ─┐
│ 成员（6 角色 + 当前成员）                                     │
│ [●产品经理 opc-product] [●UI 设计师 opc-design] [●全栈开发 opc-dev] … │
│ [◐测试工程师 执行中] [○项目经理 Agent 空闲] [○运维]            │
│                                                              │
│ [＋ 指派任务]  [按角色自动选]                                 │
│                                                              │
│ 最近指派                                                      │
│ · 修复登录态回归      → opc-qa   执行中   关联：测试验收   3 分钟前 │
│ · 补充空态截图        → opc-design 已完成  临时任务        12 分钟前│
│ · 检查依赖许可证      → opc-dev  已派发   关联：开发实现   1 小时前 │
└──────────────────────────────────────────────────────────────┘
```

- 成员 chips：状态点四态（**空闲/执行中/阻塞/离线**），显示「角色 + 成员名」；点击 chip = 预填「交给」并打开指派弹层。
- 「打开团队面板」：跳转 Harness 原生 Agent Team 面板（成员实时状态、共享任务依赖、写范围以原生面板为准）。
- 最近指派：默认 5 条，可展开全部；点击一行打开详情（状态时间线、产物、操作）。

### 4.2 指派弹层（表单）

```
指派给 Agent
──────────────────────────────
交给 *        [角色/成员下拉：产品经理 / UI 设计师 / 全栈开发 / 测试 / 项目经理 Agent / 运维 / 当前成员… / 新建 Agent…]
                └ 新建时：名称 + 角色 + 初始任务说明（由 Lead spawn）
任务标题 *    [一句话结果，例如「修复登录态刷新丢失」]
详细说明 *    [背景 / 现状 / 期望行为 / 不做范围]
验收标准 *    [可勾选/可观察条件；默认带一条「产物落盘 + 自测通过」]
关联阶段      [自动判断 / 需求分析 / UI 设计 / 开发实现 / 测试验收 / 验收复核 / 人工确认 / 运维发布 / 不关联（临时任务）]
                └ 关联阶段：走流水线双复核；临时任务：只在本对话汇报，不改流水线
期望产物      [可选，例如 docs/pipeline/engineering-research.md 或 src/...]
优先级        [P0 / P1 / P2]
附件          [可选：截图/日志（复用现有附件上传）]
──────────────────────────────
提示：派发后由 Lead 编排执行；阶段任务需要你在流水线面板审批，模型不能代批。
[取消]                                      [指派给 Agent]
```

- 校验：标题/详细说明/验收标准必填；选择「关联阶段」时若当前流水线已完成 → 提示需先发起变更轮或改为临时任务；若阶段不是当前可启动阶段 → 提示将按「排队/重做」处理，由 Lead 决定。
- 派单消息（发到当前对话）模板（结构化、可被 Lead 直接执行）：

```text
【工作台指派 · 第 N 轮】
交给：<角色/成员 opc-xxx>（新建则写明 spawn 参数）
任务：<标题>
背景/期望：<详细说明>
验收标准：<逐条>
关联阶段：<阶段 id 或「临时任务」>
期望产物：<路径，可空>
优先级：<P0/P1/P2>
执行要求：按角色边界执行；阶段任务走 pipeline_* 闸门；临时任务完成后在对话汇报产物与验证；
        不要越过 approval/release 人工闸门；完成后更新工作台指派状态。
```

### 4.3 指派状态与状态机

```
draft → dispatched（已派发，等待 Lead 执行）
      → running（进行中：Lead 已接单/成员开工）
      → review（待你确认：完成汇报，Owner 可打回/通过）
      → done（已完成）/ failed（已打回，可再指派/重试）/ cancelled（已取消）
```

- 临时任务（不关联阶段）：`dispatched → running → review → done`，不改变 `.dsh/pipeline.json`。
- 关联阶段任务：状态与流水线阶段联动（阶段 active/review/approved 映射到 running/review/done）；Owner 仍要在流水线面板审批。
- 操作：查看对话（定位到派单消息）、催办（向对话发一条提醒）、打回（写原因 → 状态 failed → 可重派）、取消、复制指派单。
- 超时：`running` 超过阈值（如 30 分钟）显示「等待中」提醒，不自动失败（Agent 可能长时间运行）。

### 4.4 数据与接口（实现层）

- 数据文件：`.dsh/agent-assignments.json`（按工作区隔离、不进 Git、原子写、上限 100 条/工作区 + 单条字段上限；参照现有 `.dsh/*.json` 的写入模式）。
- 模型：`{ id, round, title, detail, acceptance[], assignedTo: {role, member?, newAgent?}, stageId?, priority, expectedArtifacts[], status, createdAt, updatedAt, history[] }`。
- Host 路由：主文件路由新增 ops `assignmentList / assignmentSave / assignmentUpdate / assignmentDelete`（与 pipeline 同级；校验 root、字段、上限；SSH 工作区返回不支持）。
- 客户端：Workbench 卡片 + 弹层（复用 `ds-wb-*` / `ds-btn` / `ds-pipe-*` 样式与 i18n）；派单用现有 `sendPromptText`；状态卡点击时更新记录。
- 状态来源：MVP 由 Owner 手动推进（完成汇报后点「标记完成/打回」）+ 关联阶段从 `pipelineDoc` 推导；原生成员实时状态交给团队面板（B 路线后续）。

### 4.5 与流水线/双复核的关系

| 指派类型 | 是否需要流水线 | 闸门 |
|---|---|---|
| 关联阶段（产品/设计/开发/测试/验收/运维） | 是，走现有七阶段 | 不变：acceptance AI 复核 → **Owner 人工确认** → release 才启动 |
| 临时任务（修复小 bug、补截图、调研、清理文档） | 否 | 完成后由你确认；若发现需要改需求/范围 → 建议转「需求与调整」或发起变更轮 |
| 新建 Agent | 由 Lead `spawn_teammate` 创建（受 Harness 团队上限约束） | 不改变闸门 |

## 7. 验收标准（建议）

1. 工作台出现「团队与指派」卡，展示 6 角色成员（状态四态）与最近指派记录。
2. 点「指派任务」打开弹层；标题/详细说明/验收标准必填，未填不能提交。
3. 提交后当前对话收到结构化指派单（含角色、任务、验收、关联阶段、期望产物、执行要求），并可在工作台看到 `dispatched` 记录。
4. 选择「关联阶段」时提示双复核闸门；流水线状态不会被指派动作直接改写（必须走 `pipeline_*` 闸门）。
5. 临时任务不改变 `.dsh/pipeline.json`；完成后 Owner 可标记 done 或打回（打回需写原因并可重派）。
6. 指派记录持久化在 `.dsh/agent-assignments.json`，刷新/重启后仍在；超过上限/字段非法有明确错误。
7. 中英文完整；SSH 工作区提示不支持；无成员/Lead 不在时给出可操作提示（先打开团队面板或先发起对话）。
8. 不引入新的运行时依赖；不重复实现团队面板；不破坏现有流水线/验收/交付功能。
9. （可选）点击「打开团队面板」可跳到原生 Agent Team 面板查看成员实时状态与共享任务。

## 8. 风险与后续

| 风险 | 影响 | 缓解 |
|---|---|---|
| 指派消息被 Lead/模型忽略细节 | Agent 做偏 | 结构化模板 + 必填验收 + 派单回执（Lead 回「已接单」）；卡片显示状态 |
| 成员名跨会话变化 | 指派记录指向旧名 | `assignedTo.role` 为主、member 为可选；新会话提示「成员已重建」并允许按角色重派 |
| 没有实时成员状态 | Owner 误判空闲 | 明确「打开团队面板」为状态权威；MVP 卡片状态以指派记录+阶段推导 |
| 临时任务滥用绕过流水线 | 质量风险 | 默认「自动判断」引导关联阶段；临时任务要求验收标准与产物；不涉及代码/需求改动才允许 |
| 插件与原生团队 UI 重复 | 维护成本/不一致 | 只做项目侧指派器；成员/共享任务能力链接原生面板（B 路线等 API） |
| 原生 TeamService 无 owner API | B/C 路线受阻 | 如实说明；先交付 A，等上游能力再升级 |

**后续路线**
1. MVP（A）落地后收集 Owner 使用反馈；
2. Harness 暴露 owner 级团队 API 或事件后，做 B：卡片直接显示成员实时状态/当前任务，并提供「催办/查看成员会话」；
3. 再评估 C（直接派工/建共享任务），前提是不破坏「Lead 组队 + Owner 审批」的权限模型。
