## 1. 关键交互决策（与 Lead MVP 对齐）

1. **不新造 Agent 运行时**：表单提交 = 生成**结构化指派单**发到当前对话，由 Lead 用原生 `spawn_teammate` / `send_message` / `team_task_*` 执行；插件只做「项目侧指派器 + 状态桥」。
2. **卡片位置**：放在「项目状态」与「项目流程」之间（与提案一致）——「需要你处理」保持最上、注意力最高；团队/指派属于项目级上下文，不打断闸门操作。
3. **交给谁 = 角色优先**：默认「按角色」派给该角色当前成员（如 `opc-qa`）；也支持「当前成员」「新建 Agent（名称 + 角色，由 Lead spawn，受团队上限约束）」。点成员 chip = 预填并打开弹层。
4. **任务类型二分**：
   - **关联阶段**（需求/设计/开发/测试/验收复核/发布）：走现有七阶段与**双复核闸门**；指派动作**不直接改写** `.dsh/pipeline.json`，阶段仍需 Owner 在流水线审批。
   - **临时任务**（不关联）：不改变流水线，完成后**由 Owner 确认**（通过/打回），结果只在对话汇报。
   - **人工确认 / 发布不可直接指派**（Owner 闸门），在表单内明确提示。
5. **状态来源分层**：MVP 下指派人/状态以插件本地记录（`.dsh/agent-assignments.json`）为准；关联阶段的状态从 `pipelineDoc` 推导；**成员实时状态以 Harness 原生团队面板为权威**，卡片提供「打开团队面板 ↗」，不重复实现团队通信。
6. **状态机**（与提案一致）：`draft → dispatched（已派发/等待 Lead）→ running（执行中）→ review（待你确认）→ done（已完成）/ failed（已打回，可再指派）/ cancelled`。UI 把 `dispatched` 拆成「已派发 → 等待 Lead」两段，让 Owner 看见「消息已发但 Lead 还未接单」。
7. **操作留痕**：查看对话 / 催办 / 打回 / 再指派都会追加记录；打回必须写原因（弹窗内二次确认，静态稿体现为按钮与提示），不自动重派。
8. **对齐现有风格**：复用 `ds-wb-*` 卡片（白底、12px 圆角、1px 边框、20px 内边距）、`ds-btn`、语义色近似值；不引入新组件库。
9. **响应式**：桌面 1440 下内容 max-width 1080 居中、卡片全宽；≤1080 卡片转单列，成员 chips 自动换行；≤768 抽屉变全宽底部面板、按钮高度 ≥44。草案仅画桌面，移动端按此规则实现。
10. **可访问性**：状态「颜色 + 文字 + 形状」三重表达；焦点环 2px `#4176e6` + 2px offset；主按钮 / 输入 44px 高；Tab 顺序：弹层标题 → 交给谁 tabs → 角色 chips → 标题 → 说明 → 验收 → 优先级 → 阶段 → 产物 → 附件 → 取消 → 指派；Esc 关闭并归还焦点。

## 7. 可访问性说明

- **状态不靠颜色**：成员/任务状态均有文字；进度节点有 ✓ 或标签；打回红色同时有「已打回」文字与操作。
- **焦点**：标题输入展示 2px `#4176e6` 焦点环 + 2px offset；实现时 `:focus-visible`，不 `outline:none` 无替代。
- **键盘**：弹层打开后焦点进入标题 → Tab 顺序到取消/提交；Esc 关闭并把焦点还给「指派任务」；抽屉为 `role="dialog" aria-modal="true"`，背景不可聚焦。
- **可读名称**：图标按钮（关闭/附件/团队面板）带 `aria-label`/`title`；成员 chip 是 button，`aria-label="指派任务给 测试工程师 opc-qa"`。
- **触控目标**：主按钮/输入 44 高；成员 chips 34 视觉 + 44 命中区（padding）；行内链接 ≥32 高。
- **屏幕阅读器**：进度用 `aria-label="进度：已派发，等待 Lead，执行中，待你确认，已完成；当前执行中"`；状态 pill 有文本；错误/成功提示 `aria-live="polite"`。
- **对比度**：见 §5.1，所有信息文本 ≥4.5:1，非文本 ≥3:1（空闲点 3.63:1）。
