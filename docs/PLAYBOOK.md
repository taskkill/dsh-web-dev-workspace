# Playbook：从一个需求到客户交付（双复核模式）

> 适用版本 **v1.2.72**。插件：Dev Workspace（`@local/dsh-web-dev-workspace`）+ Harness 原生 Agent Teams。
> 角色分工与闸门细节见 [AGENT_TEAM.md](AGENT_TEAM.md)；团队编制、角色边界手册与立项话术见 [opc/](opc/README.md)；功能复测步骤见 [ACCEPTANCE.md](ACCEPTANCE.md)。

一次完整交付 = **1 个需求 → 7 个流水线阶段 → 双复核（AI 项目经理验收复核 + 你的人工确认）→ 1 次发布 → 1 套交付包**。

## 极简用法（你只需要做 3 件事）

1. **给需求（可带截图/需求文档）**：打开工作区默认落在**全宽「工作台」页面**——把需求文字贴进「需求录入」，把截图或需求文档拖进虚线框（或点「添加附件」），保持「自动推进」勾选，点 **「交给产品经理」**。产品经理会把它梳理成可落地方案（需求文档 + 验收项）并启动流水线，之后设计/开发/测试/AI 验收复核自动推进；你只在**人工确认**与**发布**两个闸门出现。
2. **只过两道人工闸门**：快速模式可在工作台直接勾选；中间五阶段自动通过，工作台「需要你处理」会出现人工确认按钮（或流水线顶部横幅），点 **通过 / 打回** 即可。确认前先看 `docs/pipeline/acceptance-review.md`（AI 项目经理的复核结论）。
3. **收交付**：全部通过后，验收面板「导出验收报告 / 打包交付 / 预览分享」，把报告、包和链接交给客户。

> 下面的完整流程是给 Lead 和团队看的；你不需要记阶段名、工具名或提示词。



## 0. 开始前（2 分钟）

1. **重启一次 Harness**（加载 Host 路由与模型工具），刷新页面。
2. 打开一个**本地工作区**（SSH 工作区不支持流水线/验收/交付）。
3. 侧栏确认能看到：**任务 / 验收 / 流水线** 三个标签。
4. 清理上一轮（如果这个工作区做过交付）：
   - 让 agent 调 `acceptance_clear_passed`，或验收面板里删除旧项；
   - 流水线目前**没有重置按钮**：新项目建议开一个新工作区；同一工作区重来需先删除 `.dsh/pipeline.json`。

## 1. 角色与工位

| 角色 | 谁执行 | 在插件哪里 | 关键工具/面板 |
|---|---|---|---|
| 产品经理 | 子代理 / Lead | 流水线（需求 + 产品阶段） | `pipeline_*`、`acceptance_add` |
| UI 设计师 | 子代理 / Lead | 流水线 + 编辑器/预览 | 设计文档、图片预览、内置浏览器 |
| 全栈开发 | 子代理 / Lead | 任务、Git、编辑器 | 任务面板、Problems、Git diff |
| 测试工程师 | 子代理 / Lead | 任务、验收、证据 | 任务面板、`acceptance_update`、证据上传 |
| **项目经理 Agent** | 子代理 / Lead | 流水线（验收复核关）、验收、Git | `acceptance_list/report`、`task_run` 复测、`pipeline_submit_stage(acceptance)` |
| 项目经理（你，Owner） | 你 | 流水线、验收、Git | 通过/打回（人工确认）、验收勾选、审阅标记 |
| 运维 | 子代理 / Lead | 流水线 + 交付 | `pipeline_record_release`、交付包、预览分享 |

## 2. 完整时间线

### ① 下发需求（你）

流水线面板填「需求标题 + 需求描述」并保存（或让 agent 调 `pipeline_set_requirement`）。描述里至少写清：
**目标用户 / 场景 / 范围（做什么、不做什么）/ 关键验收标准 / 约束（技术栈、兼容性）**。

> 例子：*「给现有 React 管理后台加登录页：邮箱+密码、记住登录、错误提示；复用现有 UI 组件；不接真实后端，用 mock；验收：三种错误分支可见、刷新后保持登录态、移动端可用。」*

### ② 产品经理阶段

- 面板点「启动并派发」（或 agent 调 `pipeline_start_stage({stageId:'product'})`），对话会收到该角色的提示词。
- Lead 用 `spawn_teammate` 组建产品经理（或在当前会话直接执行），成员按提示词产出：
  - `docs/pipeline/requirements.md`（目标、用户故事、范围、验收标准）
  - 用 `acceptance_add` 拆出可勾选验收项（title 写结论、requirement 写验证条件、category 分组）
- 完成后调 `pipeline_submit_stage({stageId:'product', summary, artifacts:[{path:'docs/pipeline/requirements.md',label:'需求分析'}]})`。
- **闸门 1（你）**：流水线面板看摘要与产物 → 写评审备注 →「通过」或「打回」。

### ③ UI 设计阶段

- 启动 `design` → 设计师产出 `docs/pipeline/design.md`（信息架构、页面/组件、交互、视觉规范）+ 设计资源；**有 UI 界面时必须提交界面截图/高保真稿**（PNG/JPG/SVG 或 HTML 静态稿，放 `docs/pipeline/design/`），工作台「设计稿」卡片与流水线产物会显示缩略图，直接点开看图。
- 提交 + artifacts（例如设计说明 + 关键页面截图路径）。
- **闸门（你）**：通过 / 打回（打回备注写清要改什么）。

### ④ 开发实现阶段

- 启动 `development` → 开发按需求 + 设计实现代码。
- 过程中用：**任务面板**跑 build/test、**Problems** 点击跳错、**Git 变更列表**审阅+「已审」标记、终端/任务日志。
- 提交：`pipeline_submit_stage({stageId:'development', summary, artifacts:[...代码/构建记录路径]})`。
- **闸门（你）**：看变更（Git 已审标记）→ 通过 / 打回。

> 小需求可以合并角色，但流水线顺序不能跳：设计阶段写「无 UI 变更」也要走一遍闸门。

### ⑤ 测试验收阶段

- 启动 `testing` → QA 写 `docs/pipeline/test-report.md`，跑任务面板里的测试/构建，逐条复测验收清单。
- 用 `acceptance_update` 把结果回填 `pass` / `fail`（fail 写复现与原因，外部依赖写 `blocked`）。
- 证据（截图/日志）上传到 `.dsh/evidence/` 并附到对应验收项备注。
- 提交测试报告 + 证据路径。
- **闸门（你）**：验收面板逐项看 pass/fail、证据缩略图；通过或打回。

### ⑥ 验收复核（项目经理 Agent，双复核第一关）

- 启动 `acceptance`（`pipeline_dispatch({stageId:'acceptance'})` 会给出项目经理 Agent 的完整提示词与 `docs/opc/05-review.md` 手册）。
- 项目经理 Agent 做**项目级复核**，只读 + 复测，不改代码/需求/验收标准：
  - 读需求与 `docs/pipeline/requirements.md`，核对需求点覆盖；
  - `acceptance_list` / `acceptance_report` 逐项核对状态、证据与复测轮次，列 fail/blocked/缺证据；
  - 跑与测试阶段一致的复测命令（`task_detect` → `task_run`）；
  - 检查 Git 变更与「已审」标记、关键文件 diff；
  - 对照宪章 DoD 七项；
  - 产出 `docs/pipeline/acceptance-review.md`（逐项核对表 + 复测证据 + DoD + **建议放行 / 建议打回**），并在 summary 写清结论、阻断项与建议回退阶段。
- 提交 `pipeline_submit_stage({stageId:'acceptance', summary, artifacts:[{path:'docs/pipeline/acceptance-review.md',...}]})`。快速模式下自动通过并推进到人工确认；普通模式下停在待评审，由你通过/打回。
- **双复核点**：Agent 只能给建议，**不能审批**；是否放行由你在下一关决定。

### ⑦ 人工确认（第二道复核，只有你能过）

- 启动 `approval`（agent 可启动，但**没有审批工具**）。
- 你核对：`docs/pipeline/acceptance-review.md` 的结论与证据、验收清单是否全 pass、变更是否已审、测试报告与证据是否齐全、预览是否可用。
- 面板点「通过」→ **发布阶段解锁**；不通过就写备注打回（可连同 acceptance 一起打回并回退到 development/testing）。

### ⑧ 发布上线（运维）

- 启动 `release` → 运维执行构建/上传/部署（在任务面板或终端里）。
- 发布完成后：`pipeline_record_release({environment, url, notes})`（记录环境、可访问链接、版本/回滚说明）。
- 需要给客户临时看效果时：验收视图「预览分享」输入 dev server 端口 → 生成 token 链接 → 复制给客户。
- 提交 release 阶段摘要 + 发布记录。

### ⑨ 客户交付（你）

在验收面板一键产出：

1. **导出验收报告**（Markdown，含统计与未通过项清单）；
2. **证据包**（`.dsh/evidence/` 里的截图/日志，报告备注里带路径）；
3. **打包交付**（构建产物 + `ACCEPTANCE.md` → `.dsh/deliveries/*.zip`，交付记录可再次下载）；
4. **预览分享链接**（客户可直接打开的 HTTP 链接，含 HMR）。

### ⑩ 收尾

- 客户确认后：`acceptance_clear_passed` 清理已通过项（下一轮从干净清单开始）、关闭预览分享、Git 提交/推送。
- 把结论、客户反馈、遗留风险写进对话或工作区记忆（`memory_save`），下一轮交付可直接继承。


## 进行中调整需求：追加 / 修改 / 完善

不需要等到交付，项目进行中就可以修订需求。工作台顶部有独立的**「需求与调整」**卡片（需求正文 + 追加 / 修改 / 发起变更三个按钮 + 修订记录），入口不再藏在状态卡的小链接里：

| 模式 | 适用 | 效果 |
|---|---|---|
| **追加说明** | 补充细节、边界、验收说明 | 追加到需求详情，不改范围；通知产品经理吸收到需求文档与验收项 |
| **修改需求** | 需求写错/范围调整 | 直接更新需求标题与内容；若当前阶段已在进行，可能需要打回该阶段重做 |
| **新轮变更** | 项目七关全部完成后的大调整 | 归档本轮快照，重置七关；发起时可选**适用范围**（见下） |

变更轮次的「适用范围」：

| 范围 | 走哪些关 |
|---|---|
| **完整七关** | 需求 → 设计 → 开发 → 测试 → 验收复核 → 人工确认 → 发布 |
| **仅产品调整** | 只重做需求与验收项：需求 → 完成。设计/开发/测试/验收复核/人工确认/发布跳过（适合只改需求文档/验收标准） |
| **仅设计调整** | 只重做设计：跳过需求，设计 → 完成。开发/测试/验收复核/人工确认/发布跳过（适合只改设计稿） |
| **产品与设计** | 重做需求与设计：需求 → 设计 → 完成。开发/测试/验收复核/人工确认/发布跳过 |
| **仅开发调整** | 跳过需求与设计：开发 → 测试 → 验收复核 → 人工确认 → 发布（适合代码/配置调整） |
| **仅发布调整** | 跳过需求/设计/开发/测试/验收复核：人工确认 → 发布（适合发布物调整） |

跳过的阶段会以「跳过」标记保留在流程里（带原因），方便交付时说明「本次不涉及」。

每次修订都会写入「**需求修订记录**」（类型 + 时间 + 摘要），工作台项目卡显示最近 3 条，流水线视图显示最近 6 条；产品经理会收到一条「吸收本次需求修订」的派发，更新 `docs/pipeline/requirements.md` 与验收项，如果和当前阶段产出冲突会说明需要打回哪一关，由你决定。

## 交付后调整：变更轮次

项目七关全部通过后，如果有客户反馈或新调整：

1. 工作台「当前项目」卡片 → 点 **发起变更**
2. 填「变更标题 / 变更内容（要调整什么、验收标准）」→ 点 **发起第 N 轮变更**
3. 系统会自动：
   - 把上一轮七个阶段的摘要快照存入「历史轮次」（最多保留 10 轮，可追溯）
   - 阶段全部回到未开始，需求更新为本次变更，发布记录与验收项保留
   - 派发产品经理梳理本次变更（需求分析 → 验收项）
4. 之后走正常流水线：设计 → 开发 → 测试 → **验收复核** → **你确认** → 发布（运维记录新版本）
5. 每一轮独立审批、独立发布记录；上一轮的产物仍在 Git / 交付记录里

> 一个工作区只承载一个项目（含它的多轮变更）；完全独立的新项目建议开新工作区。

## 3. 可以直接发给 Lead 的指令模板

派发一个阶段时，把下面这段发到对话即可（把 `<阶段>` 换成 product/design/development/testing/acceptance/approval/release）：

```text
按交付流水线执行 <阶段> 阶段：
1) 先调 pipeline_status 确认当前阶段与上游产物；
2) 调 pipeline_stage_prompt({stageId:'<阶段>'}) 拿到该角色的完整边界与交付物要求；
3) 用 spawn_teammate 为该角色创建一名队友（name/description 体现角色，prompt 用上一步的提示词 + 工作区路径），
   需要并行时用 team_task_create 拆任务并用 blocked_by 表达顺序；
4) 只做该角色边界内的事；完成后自检：
   - 产出是否落在工作区、验收项是否用 acceptance_add/acceptance_update 维护；
   - 开发/测试阶段是否用任务面板跑过 build/test 并处理 Problems；
   - 验收复核阶段是否逐项核对验收清单与证据并写出 docs/pipeline/acceptance-review.md；
5) 最后调 pipeline_submit_stage 提交 summary 与 artifacts，等待项目经理审批。
注意：你不能审批，也不要开始下一阶段。
```

## 4. 你（项目经理）每阶段要做的三个动作

1. **看**：摘要 + 产物链接 + 验收清单 +（验收复核关）`docs/pipeline/acceptance-review.md` +（开发阶段）Git 变更已审标记。
2. **问**：需要时在评审备注里写打回原因；让 agent 修完重新提交。
3. **点**：通过 / 打回；只有你能让流水线前进，也只有你能批准发布。

## 5. 交付物清单（客户拿到什么）

| 交付物 | 来源 |
|---|---|
| 需求与设计说明 | `docs/pipeline/requirements.md`、`docs/pipeline/design.md` |
| 验收复核报告 | `docs/pipeline/acceptance-review.md`（AI 项目经理逐项核对 + DoD + 放行建议） |
| 可运行/可访问的成果 | 预览分享链接、发布 URL（`pipeline.releases`） |
| 验收报告 | 验收面板「导出验收报告」（Markdown） |
| 证据 | `.dsh/evidence/` 截图/日志，报告里带路径 |
| 交付包 | `.dsh/deliveries/*.zip`（构建产物 + ACCEPTANCE.md），交付记录可查 |
| 发布记录 | `.dsh/pipeline.json` 的 `releases`（环境/URL/说明/时间） |

## 6. 常见问题

- **每次都要重启 Harness 吗？** 只有升级插件后第一次需要（Host 路由/工具）。之后刷新页面即可。
- **能跳过某个阶段吗？** 不能。小需求可以把该阶段产物写得很小（例如设计阶段写「无 UI 变更」），但仍要过闸门；验收复核关始终会跑。
- **agent 能自己批准吗？** 不能，也没有审批工具；只有你在面板点通过。项目经理 Agent 只给「建议放行 / 建议打回」。
- **双方意见不一致怎么办？** AI 复核建议放行但你认为不行 → 你打回并写备注；AI 建议打回但你认为可放行 → 你仍可选择通过，但要记下理由（原则上以你的决定为准，报告里的阻断项应被处理或明确承担风险）。
- **上下文太长怎么办？** 每个阶段用独立子代理或新会话；用 `pipeline_status` / `pipeline_stage_prompt` 按需读取，而不是把整条流水线塞进上下文。
- **SSH 工作区能用吗？** 流水线/验收/交付目前只支持本地工作区。
- **旧版本六阶段项目怎么办？** 升级后自动兼容：进行中的项目会多出一关待开始；旧版已完成项目该关显示「升级迁移」通过，不会卡住变更轮。
- **同一工作区第二次项目？** 流水线没有重置按钮，建议新项目开新工作区；或在确认交付完成后删除 `.dsh/pipeline.json` 再开始（验收清单用 `acceptance_clear_passed` 清理）。
- **公网客户看不到预览链接？** 预览分享是 Host 随机端口的 token 链接，公网需要该端口可达（或后续接隧道）。
